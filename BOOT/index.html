Boot Experience

RoFrame's opt-in boot system coordinates real startup work in Core. BootScreen (Core UI) and CartoonBootScreen (Cartoon UI) render the same state. Games own the name, logos, theme and optional sound. Powered by RoFrame is off by default. The Core entry point remains server-safe and does not load React or Cartoon UI.

Minimal client setup​

import { RoFrame } from "@frameactive-studio/core";
import { mountBootScreen } from "@frameactive-studio/core/ui";

const boot = RoFrame.configureBoot({
    minDisplayTime: 1.25,
    introDuration: 0.45,
    longLoadThreshold: 6,
    fadeOutDuration: 0.35,
});

// Mount before discovering controllers; UIController is not required here.
const screen = mountBootScreen({ boot, gameName: "My Game" });
script.Destroying.Once(() => screen.destroy());

// Register game tasks before this call. Runtime begins boot automatically.
void RoFrame.startClient(script);

Boot is disabled in the runtime until configureBoot() is called. Configure once before startup; it returns the same RoFrame.boot instance, preserving signal subscriptions. For isolated use, construct new Boot(options) and call begin(). Core automatically tracks framework (systems/discovery), components and modules, weighted 20/5/10. These IDs are reserved by configureBoot(). A framework startup failure remains visible and is not retryable: lifecycle hooks may have side effects and cannot safely be replayed blindly.

Tasks and real progress​

Register every task before begin() or startClient(); registration is sealed once startup begins. Each task has a unique nonempty id, a finite positive weight, optional display label, optional timeout in seconds, and either a run callback or manual lifecycle completion. Modules can export a registration helper that a game's bootstrap calls before startup. Do not register tasks from module init/start hooks, which execute after boot has begun.

boot.register({
    id: "first-view-assets",
    label: "Boot.Assets",
    weight: 15,
    timeout: 20,
    retryable: true,
    run: async (context) => {
        await assets.preload(["Brand.Logo", "UI.Inventory"]);
        if (!context.isActive()) return;
        // Optional game work; successful return completes this task.
    },
});

AssetRegistry.preload() uses ContentProvider.PreloadAsync(). Select important first-view assets; do not preload the whole game. An indivisible load can remain at zero until it completes. For measurable batches, use context.setProgress(completed / total) after actual work. The global progress is sum(weight * progress) / sum(weight). Never advance it using a timer.

Automatic callbacks start concurrently during begin(), including while the intro plays. Manual tasks use start(id), setTaskProgress(id, 0…1), complete(id) and fail(id, safeErrorCode). A value of 1 alone does not complete a task. start() arms the task's timeout; pending manual tasks have no timer yet.

States and timing​

Idle → Intro → Loading → Ready → Finished; failed work changes the state to Failed. A retry restores Intro or Loading unless another task is still failed. Successful tasks retain their progress across retries.

Ready requires every task to be complete, intro completion, and the minimum display time. Finished follows after fadeOutDuration, even when no UI is mounted. The UI only animates that transition; a missing image cannot block gameplay. After longLoadThreshold, longLoading becomes true. This is informational and does not fail a task. Only explicit failure or a task-specific timeout fails boot.

The built-in logo presets are fade, scale, pop, slide, and none. reducedMotion: true selects a fade and disables spinner rotation. Pass introDuration: 0 and fadeOutDuration: 0 when no animation is wanted.

A custom intro: () => Promise<void> in Core options runs after the built-in intro duration. Its resolution ends Intro. Rejection, synchronous failure or a five-second safety deadline also ends Intro, so cosmetic code cannot strand boot. Use zero built-in duration when the custom intro owns the entire sequence. Own custom animation resources in a Cleanup and release them on boot.destroying. Optional intro audio belongs to the game: play it through AudioManager with the game's volume settings, and destroy its handle during cleanup. No sound is played by default.

PlayerReady, persistence and normal UI​

Boot tasks are local to a client or server; they do not automatically replicate. A global server boot must not wait for all future players. Server profile loading remains owned by PlayerLifecycle and persistence.

For client readiness, register a manual task before startup, start it when your readiness subscription is installed, and complete it only after an authoritative server readiness handshake. Do not trust a client-selected player or a client claim that their profile is ready. Subscribe before requesting the handshake; the server should remember readiness and answer clients that connect late.

Coin Hunt demonstrates this in its client boot and controller:

  1. Mount the boot screen before runtime discovery.
  2. Start the profile task and request HUDReady.
  3. DemoProfileService sends SessionReady only after server PlayerReady.
  4. Complete profile, then load profile and round replicas under stores.
  5. Keep the regular HUD hidden until boot.finished.

The mounted screen sinks native character actions while keeping GUI selection and Retry available. It does not disable CoreGui or change the camera. Gate custom game actions separately using boot.read().state === "Finished" and subscribe to finished before reading the current state to avoid missing a fast boot. Server gameplay still needs its normal authoritative readiness checks. startClient() resolves when framework hooks finish; use finished to release presentation/gameplay after additional asynchronous boot tasks and fade complete.

Branding and themes​

import React from "@rbxts/react";
import { mountBootScreen } from "@frameactive-studio/core/ui";
import { CartoonBootScreen, CartoonThemeProvider } from "@frameactive-studio/cartoon-ui";

const props = {
    boot,
    gameName: "My Game",
    branding: {
        logo: assets.get("Brand.Logo"),
        studioLogo: assets.get("Brand.StudioLogo"),
        showPoweredByRoFrame: false,
    },
    logoAnimation: "pop" as const,
    loader: { showProgress: true, showPercentage: true, showStage: true, showSpinner: false },
};
const screen = mountBootScreen(props,
    <CartoonThemeProvider>
        <CartoonBootScreen {...props} />
    </CartoonThemeProvider>);

Logo strings are resolved content IDs from the game's asset registry, not registry keys. No RoFrame logo is supplied. The game name remains visible when a logo is missing or cannot load. An optional studio image is subordinate to the game logo. Attribution, when explicitly enabled, appears in small muted type at the bottom.

BootScreen has a neutral default and accepts partial theme overrides: background, surface, text, mutedText, accent, font, and radius. CartoonBootScreen reads the existing Cartoon theme provider and accepts the same overrides. Its animation default follows the theme's enabled setting.

The screen background covers the entire viewport (ScreenInsets.None), including the area behind the Roblox top bar and device cutouts. A native ScreenArea keeps its interactive content within CoreUISafeInsets; it updates on viewport and inset changes without polling. Content uses a bounded width/height. Retry receives native controller selection with a visible focus border, and previous focus is restored when appropriate. Games can render <BootScreen {...props} /> in their own React root instead of using the mount helper; they then own input blocking, root lifetime and subscription cleanup.

Errors and retry​

Callbacks that reject or throw fail with BOOT_TASK_FAILED. Timeouts use BOOT_TASK_TIMEOUT. Manual callers may supply safe public codes such as PROFILE_LOAD_FAILED. Do not pass stack traces or secrets as error codes. Snapshots do not retain raw rejection values. Log developer diagnostics in the game's task callback before rethrowing if needed.

Set retryable: true with run to repeat an automatic task, or supply a separate retry(context) callback for an initially manual task. boot.retry(id) restarts only that failed task and resets its timeout/progress. The UI offers Retry for retryable failed tasks, and a rejoin message for unsupported failures. With multiple failures, every failure must be resolved before Ready.

Each callback gets an attempt-scoped context.isActive() and setProgress(). After a timeout, failure, retry or shutdown, stale callbacks cannot complete or update the task. Native yielding operations themselves cannot be cancelled; check isActive() before applying game side effects. Manual async callers must apply their own attempt guard; Coin Hunt does this for store loads.

Configuration errors are structured KernelErrors: BOOT_TASK_DUPLICATE, BOOT_TASK_UNKNOWN, BOOT_INVALID_WEIGHT, BOOT_INVALID_CONFIGURATION, and BOOT_RETRY_UNSUPPORTED.

Signals, diagnostics and cleanup​

changed publishes snapshots; started, stageChanged, progressChanged, taskChanged, ready, failed, finished, and destroying expose typed Signals. read() returns a fresh snapshot with task statuses, weights, safe error codes, progress and elapsed seconds. setStage() accepts a localization key or label; pass translate(key) to the UI for game-specific text. Without a translator, built-in Boot messages and framework labels use English fallbacks. No polling or RenderStepped loop is used.

Task timings are captured when tasks start/end and can be consumed by developer logging or profiling tools. debug: true shows task diagnostics only in Studio. Analytics can connect to started/ready/failed and record one event per lifecycle transition; avoid tracking every progress update.

Own each signal connection in Cleanup. mountBootScreen() destroys its root, tweens, selection ownership and input binding on Finished or Boot destruction. Destroy its returned handle on game shutdown as well. RoFrame.stop() destroys Boot before runtime teardown. boot.destroy() invalidates in-flight callbacks, cancels all timers and disconnects all signals; it is idempotent. Visual listener errors are isolated so they do not prevent delivery to other observers.

Validation​

Automated tests cover weighted/partial progress, timing, long loading, completion, failures, retries, invalid registrations, stale attempts, cosmetic intro failure, snapshot isolation, shutdown and the actual React tree's branding/theme/error contract. Builds validate Roblox types; native layout and device behavior require Studio validation.

Manual Studio checklist (run on the freshly built place):

  • Fast startup: no flash, real 100%, one fade, HUD appears afterward.
  • Slow profile: status remains visible; Still loading after six seconds.
  • Asset delay: preload only selected first-view assets, honest partial progress.
  • Failed profile: no premature gameplay; safe code/rejoin, no raw stack.
  • Failed stores: Retry reloads stores without rerunning framework hooks.
  • Timeout then late result: stale load cannot unlock a newer attempt.
  • Phone portrait/landscape, tablet: safe insets, readable text, no clipping.
  • PC resize/ultrawide: bounded logo and progress layout.
  • Controller only: Retry selected, visible focus, activate without a mouse.
  • RoFrame attribution absent by default; unobtrusive when enabled.
  • Custom game/studio logos; missing/invalid logo still shows game name.
  • Reduced motion, each intro preset, custom intro rejection/deadline.
  • Stop during loading/retry/fade: no remaining GUI, actions or timer callbacks.
