RoFrame CLI

Phases 1–3 of the CLI masterplan provide the independent Node.js package @frameactive-studio/cli, the roframe executable, project information, structural validation and toolchain diagnostics. The CLI never executes project configuration or changes project files during inspection.

Local usage​

Requirements: Node.js 20.19+ and npm 10+. From the repository root:

npm ci
npm run build --workspace @frameactive-studio/cli
node packages/cli/dist/index.js --help
npm exec --workspace @frameactive-studio/cli -- roframe --version
node packages/cli/dist/index.js project info --cwd demo
node packages/cli/dist/index.js project validate --cwd demo --json
node packages/cli/dist/index.js doctor --cwd demo
node packages/cli/dist/index.js module create inventory --cwd demo --template full --dry-run

@frameactive-studio/cli and create-roframe are configured for public npmjs.org publication. Their source remains in the private monorepo; the runtime packages remain on GitHub Packages. No local registry upload has been performed. npm pack --workspace @frameactive-studio/cli builds a local tarball that can be installed in another project with npm install -D /absolute/path/to/frameactive-studio-cli-0.1.0.tgz. The installed executable can then be run with npm exec -- roframe --help.

Available commands​

InvocationResult
roframe, roframe help, roframe --help, roframe -hList implemented commands and options.
roframe version, roframe --version, roframe -VPrint the CLI package version.
roframe project infoReport root, workspace, installed Core/roblox-ts/module packages and config locations.
roframe project validateCheck project structure, configuration, package presence and source imports.
roframe doctorAdd Node.js, npm and Rojo host version checks.
roframe module create <name>Create a disabled module from a named template.
--cwd <directory>Find the project upward from this directory, without changing the process working directory.
--jsonEmit a machine-readable inspection report or error envelope.
--strictFail validate/doctor on warnings as well as errors.
--verbose or ROFRAME_DEBUG=1Enable diagnostics on stderr.

No command prompts. Validate/doctor exit with 1 when errors are found, or when --strict is supplied and warnings are found. Otherwise they exit with 0. project info succeeds when inspection completes, even if its report contains project errors. Usage and discovery errors exit with 1 for every command.

JSON mode writes one report to stdout, including when validation fails. A failure before inspection completes returns { "error": { "code", "message", "hint" } }. Verbose output stays on stderr. Text mode prints errors to stderr and other report lines to stdout.

Project discovery​

The exported findProjectRoot(startDirectory) API searches upward, choosing the nearest package.json with a RoFrame, roblox-ts or default Rojo marker. It recognizes the current @frameactive-studio/core scope and the masterplan's @roframe/core scope. It skips unrelated npm packages and fails on malformed package manifests. Project configuration is never executed during discovery. Compatibility checks currently support Core 0.1.x, Core 0.2.x and roblox-ts 3.x. The doctor requires Node.js 20.19+, npm 10+ and Rojo 7+ on PATH. Host tools are called with --version, no shell, a five-second timeout and bounded output. They run from the project directory so Rokit can resolve its configured version.

Checks and configuration​

Inspection checks:

  • Package dependency shape, installed versions, missing RoFrame packages, duplicate Core runtimes and missing required peer packages. Metadata is read directly without loading installed JavaScript or Luau.
  • Workspace membership using literal paths and */** patterns, npm lockfile JSON, package-manager declarations and conflicting lockfiles. Package-manager operations support npm in V1; yarn/pnpm detection produces a warning.
  • Inherited JSONC TypeScript configs, source/base directories, alias targets and static import/export resolution using the installed TypeScript parser.
  • Default Rojo projects (default.project.json/.jsonc), nested projects, required/optional filesystem mappings, invalid child nodes and mapping cycles. Missing generated output is an error; build before validating. See the Rojo project format and Rojo 7.7.1 path implementation.
  • Literal RoFrame.configureModules activation shapes in project source files. Dynamic expressions generate explicit warnings without being evaluated.

An optional roframe.config.json can customize future generator destinations:

{
  "paths": {
    "modules": "src/modules",
    "services": "src/server/services"
  },
  "generation": { "tests": true, "docs": true }
}

Other supported path keys are controllers, components and stores. Paths must be relative and stay within the project. These settings do not create directories during inspection. A roframe.config.ts containing export default { ... } with literal data is also supported, including as const and satisfies. Imported values, calls, spreads and variable references are rejected; project code is never evaluated. Keep only one CLI config file.

The CLI config holds tooling settings. Runtime module activation stays in RoFrame.configureModules in the existing bootstraps, as described in Modules.

Validation limits and next phases​

Structural validation does not replace tsc, rbxtsc, a Rojo build or Studio runtime tests. Installed module packages are shown without inferred activation status. Runtime registration/dependency graphs and arbitrary config validators are not evaluated. Peer package presence is checked; peer-version range solving follows in Phase 6. Stale generated files are not diagnosed yet.

The demo currently reports two warnings: its activation depends on a dynamic config value, and installed module packages cannot establish runtime registration. Normal validation succeeds; --strict intentionally fails on those warnings.

Phase 4 adds individual code generators; module management follows in Phase 5.

Module generation​

roframe module create inventory --template full --no-interactive
roframe module create "camera tools" --template client --dry-run --json
roframe module create combat --template server --path src/gameplay --no-tests

Names normalize to kebab-case paths and PascalCase class names. Invalid/reserved names, existing module packages, case-conflicting directories, symlink ancestors and paths outside the project are rejected. The default modules directory is <tsconfig rootDir>/modules; paths.modules and --path can override it. Tests/docs default on for templates that include them; CLI config preferences and --no-tests/--no-docs can omit them. Every command is non-interactive.

TemplateFiles
minimalmodule.ts, README.md
serverManifest, Service, shared config/types/index, Studio test, README
clientManifest, Controller, shared config/types/index, Studio test, README
uiClient template plus a client-only ui/index.ts entry
fullManifest, Service, Controller, shared config/types/index, UI entry, Studio test, README

The UI entry is a typed placeholder; generation does not add React dependencies. Tests are exported Studio harness functions, not automatically executed Node tests. Generated code uses the detected Core 0.1.x or 0.2.x scope and current APIs.

All destinations are printed before creation. --dry-run performs the same preflight checks and changes no files. Creation stages a complete directory, reserves the destination exclusively and renames it into place. Existing user files are not overwritten; there is no --force flag.

Modules start with enabled: false. Import/register the inert manifest, map server/client/shared code to their appropriate Rojo containers, and configure activation in the corresponding runtime bootstrap. These edits remain manual; --enable fails explicitly until Phase 5. Never map an entire full/server module into ReplicatedStorage. Generated READMEs contain registration instructions.

Project starter and public installation​

After the first npm release:

npm install -g @frameactive-studio/cli --@frameactive-studio:registry=https://registry.npmjs.org
npm create roframe@latest my-game

Private runtime and public CLI names share the same scope. npm routes by scope, so explicit CLI installation must use the npmjs.org scope override or a public tarball URL. The starter bundles its public CLI dependency to work even inside projects whose scope points to GitHub. Generated games use a public CLI tarball URL in devDependencies and keep the private runtime scope mapping in .npmrc.

The starter creates package/TypeScript/Rojo/Rokit config and client/server/shared bootstraps. It does not install packages, create Git repositories or authenticate. The generated README explains private Core access, rokit install, npm install and build steps. Use --dry-run, --json, --cwd and --no-interactive as needed. See Packaging for the two independent publishing targets.

Development checks​

npm run test:cli
npm run typecheck --workspace @frameactive-studio/cli
npm run pack:check

pack:check requires a full build first. CLI tests use temporary fixtures, including an offline tarball installation of the CLI and TypeScript dependency with executable and API smoke tests. The root npm run check includes CLI build, lint, typecheck, tests and pack checks.

New project scaffolds use Core ^0.2.0; existing Core 0.1.x projects remain supported.
