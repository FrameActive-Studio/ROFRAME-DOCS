Phase 12 Developer Tooling

Phase 12 adds opt-in profiling and read-only diagnostics for development. Tooling is disabled by default, activates only when configured before runtime startup, and refuses to activate outside Roblox Studio unless a controlled environment explicitly opts in.

All public values and types are exported from packages/core/src/index.ts.

Enable in Studio​

Configure tooling before startServer or startClient:

import { RoFrame } from "@frameactive-studio/core";

const developerTools = RoFrame.configureDeveloperTools({
	enabled: true,
	maxEntries: 200,
	maxProfiles: 256,
});

await RoFrame.startServer(script);

const snapshot = developerTools?.snapshot();
print(snapshot?.profiles);

configureDeveloperTools returns undefined when disabled or when called outside Studio without permission. RoFrame.getDeveloperTools() returns the active instance.

For automated private test servers only, allowNonStudio: true bypasses the Studio guard. Do not enable this in public production servers. Diagnostic snapshots can expose system names, Store scope keys, Player references in retained network errors, and optional Store state.

Profiler​

The profiler is manual and does not poll or bind a frame event.

const tools = RoFrame.getDeveloperTools();

const span = tools?.profiler.begin("generation:map");
generateMap();
span?.end();

const result = tools?.profiler.measure("generation:rooms", () => generateRooms());
const loaded = await tools?.profiler.measureAsync("assets:load", () => loadAssets());

Each label stores count, total, average, minimum, maximum, and latest duration. Labels are bounded by maxProfiles; calling end() repeatedly on one span records only once. clear() releases all retained profiler, lifecycle, and network samples.

Lifecycle timing​

When DeveloperTools is active, optional observers time:

  • Service and Controller construction, init, start, and destroy
  • Component construction, init, start, and destroy per Instance path
  • Module init, start, and destroy

Entries include target, name, phase, elapsed seconds, success state, and Component instance path where applicable. Observer failures are isolated from framework lifecycle. Without DeveloperTools, the managers receive no observer and do not call os.clock for timing.

Lifecycle samples are also aggregated into profiler labels such as lifecycle:service:PlayerService:init.

Dependency graphs​

Every snapshot includes separate Service, Controller, and Module graphs:

const report = RoFrame.getDeveloperTools()?.snapshot();
for (const issue of report?.dependencies.modules.issues ?? []) {
	warn(issue.code, issue.node, issue.dependency, issue.detail);
}

Graph diagnostics report missing dependencies, disabled required modules, metadata failures, and cycle members. Optional module edges remain visible but are marked inactive when their dependency is absent or disabled. The inspection functions are also independently exported as inspectSystemDependencies and inspectModuleDependencies.

Diagnostics evaluate metadata but never construct systems or initialize modules.

Store inspector​

The Store snapshot reports:

  • runtime side
  • definitions and scopes
  • persistence and destruction state
  • explicitly replicated keys
  • pending load count
  • active scope keys, versions, and custom recipient counts

State is excluded by default:

const safeReport = tools?.snapshot();
const stateReport = tools?.snapshot({ includeStoreState: true });

includeStoreState returns a top-level state copy for each live Store instance. It may contain private player data and must never be replicated, logged publicly, or enabled by default. The inspector is read-only and cannot dispatch actions or modify Store state.

Networking diagnostics​

Network snapshots expose only registry metadata:

  • network name and active side
  • registered client-to-server events
  • registered requests
  • client listener counts
  • configured rate-limit values

Payloads, request results, and successful traffic are not retained. Rejected messages and handler failures already passing through the structured Network reporter are copied into a bounded secondary diagnostic buffer. Existing game loggers continue to receive the same entries and remain independently failure-isolated.

Snapshot and retention behavior​

const report = tools?.snapshot();

Snapshots contain profiler summaries, recent lifecycle timings, recent network errors, dependency graphs, Store diagnostics, and Network registry diagnostics. Recent entry buffers use maxEntries and discard the oldest entry at capacity.

Store and Network registry information is generated on demand. Lifecycle and network-error history remains available until clear() even after framework shutdown, while live Store/Network registry snapshots naturally become empty during cleanup.

Production characteristics​

  • DeveloperTools is not created unless explicitly enabled.
  • Studio is required by default.
  • No polling, heartbeat, Remote, Roblox Instance, or UI is created.
  • Lifecycle timing branches are absent when no observer is supplied.
  • Store and Network metadata is traversed only when snapshot() or a direct inspector is called.
  • Buffers and profile labels are bounded.
  • Diagnostic callbacks cannot break gameplay lifecycle or networking.
