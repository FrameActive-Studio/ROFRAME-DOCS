Framework Kernel

Phase 2 provides RoFrame's low-overhead lifecycle kernel. Later completed phases are documented in COMPONENTS.md, NETWORKING.md, STORES.md, PERSISTENCE.md, PLAYER_LIFECYCLE.md, UI.md, CORE_UTILITIES.md, PLATFORM_SERVICES.md, MODULES.md, and DEVELOPER_TOOLS.md. The Module system is available, but no gameplay module is bundled.

Services and controllers​

Server services live below demo/src/server/services; client controllers live below demo/src/client/controllers. The runtime entrypoints discover and require every ModuleScript below those folders. Requiring a decorated module records lightweight metadata in the current runtime's registry.

import { Service } from "@frameactive-studio/core";

@Service({ priority: 100 })
export class PlayerService {
	public init(): void {}
	public start(): void {}
	public destroy(): void {}
}

Controllers use the same lifecycle with @Controller() and are available only on the client.

Constructor dependency injection​

TypeScript constructor types do not exist at Roblox runtime. Dependencies are therefore declared as class tokens without reflection and injected in matching constructor order.

@Service({
	dependencies: () => [PlayerService],
})
export class QuestService {
	public constructor(private readonly players: PlayerService) {}
}

The callback is evaluated after discovery, so declaration order does not matter. Missing dependencies and dependency cycles stop startup with structured diagnostics. Runtime lookup remains available through RoFrame.getService(PlayerService) and RoFrame.getController(UIController).

Lifecycle and priority​

Startup is deterministic:

Discover → Validate → Resolve → Construct all → Init all → Start all

Dependencies always precede dependents. Among systems whose dependencies are already ready, higher priority values run first; equal priorities are ordered by diagnostic name. Every init() completes before any start() begins. Hooks may return void or Promise<void>.

Shutdown calls destroy() in reverse startup order. Failed startup also rolls back every constructed system in reverse order.

Cleanup​

Cleanup owns callbacks, Roblox Instances, RBXScriptConnections, signals, and objects exposing destroy, Destroy, disconnect, or Disconnect. Cleanup is idempotent and LIFO.

private readonly cleanup = new Cleanup();

public init(): void {
	this.cleanup.add(workspace.ChildAdded.Connect((child) => {
		print(child.Name);
	}));
}

public destroy(): void {
	this.cleanup.destroy();
}

Signal​

Signal<TArguments> is synchronous and strongly typed. Connections are removed in constant time, listeners added during a dispatch wait until the next fire, and disconnecting listeners during dispatch is safe.

const itemAdded = new Signal<[Player, string]>();
const connection = itemAdded.connect((player, itemId) => {
	print(player.Name, itemId);
});

itemAdded.fire(player, "sword");
connection.disconnect();

Signals are for same-runtime communication. Cross-runtime communication belongs to Phase 4 Networking.

Performance notes​

  • Discovery and graph resolution run once during startup.
  • Metadata is explicit; no runtime reflection or polling is used.
  • Dependency lookup uses constructor-token maps.
  • Signal connections use a doubly linked list for constant-time disconnection.
  • The kernel creates no Roblox Instances or RemoteEvents.
