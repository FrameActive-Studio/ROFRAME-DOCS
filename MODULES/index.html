Phase 11 Module System

Phase 11 adds opt-in gameplay-module orchestration without adding gameplay itself. A module is a manifest with typed config, dependency metadata, and a small lifecycle. Roblox Services, Remotes, Stores, and UI remain the existing native-backed RoFrame systems rather than being duplicated inside the module layer.

All public values and types are exported from packages/core/src/index.ts.

Module layout​

Gameplay modules belong together under packages; do not scatter their implementation across Core directories.

packages/
  inventory/
    src/
      module.ts
      server/
      client/
      shared/
      ui/

The framework repository contains no gameplay module. Its optional presentation module, cartoon-ui, contains only shared/client UI code and maps to ReplicatedStorage.rbxts_include.node_modules.@frameactive-studio. A game should map only its shared manifest/shared code to replicated storage and project server/client implementation into their respective runtime containers. Do not map an entire module containing authoritative server code into ReplicatedStorage.

Define a module​

module.ts default-exports the result of defineModule. Names retain their string-literal type, and lifecycle context receives the inferred config type.

import { defineModule, validators } from "@frameactive-studio/core";

export default defineModule({
	name: "inventory",
	version: "1.0.0",
	description: "Inventory gameplay boundary",
	dependencies: [],
	optionalDependencies: ["analytics"],
	config: { slots: 20 },
	configValidator: validators.custom<{ readonly slots: number }>(
		(value): value is { readonly slots: number } =>
			typeIs(value, "table") && typeIs((value as { readonly slots?: unknown }).slots, "number"),
		"slots must be a number",
	),
	init: (context) => {
		print(context.side, context.config.slots);
		context.cleanup.add(() => {
			// Release module-owned resources.
		});
	},
	start: () => {},
	destroy: () => {},
});

Definitions are inert: calling defineModule does not register or initialize anything. Runtime discovery accepts either a direct definition export or a TypeScript default export.

Discovery and registration​

At startup, the RoFrame runtime searches a child folder named modules below its client or server bootstrap root. Descendant ModuleScripts named exactly module are required in full-path order and registered before module graph validation.

For explicit registration, import the manifest from runtime-safe code before startServer or startClient:

import InventoryModule from "@frameactive-studio/inventory/module";
import { RoFrame } from "@frameactive-studio/core";

RoFrame.registerModule(InventoryModule);

discoverModuleDefinitions and discoverModuleSources are available for custom project layouts and test adapters. Duplicate names and invalid manifest exports fail startup with structured errors.

Do not import decorator-based Services or Controllers as a top-level side effect of a shared manifest. Discovery must be safe even when that module is disabled. Runtime-specific work belongs in module lifecycle hooks or in code loaded by an enabled module on the correct side.

Central activation and config​

Configure activation before starting RoFrame. A boolean changes only activation; an object can override activation and replace the module's default config.

RoFrame.configureModules({
	modules: {
		inventory: { enabled: true, config: { slots: 30 } },
		quests: true,
		analytics: false,
	},
});

await RoFrame.startServer(script);

The override is a full replacement, not a deep merge. Add a configValidator whenever config can come from a dynamic source. Unknown configured module names, malformed activation values, and rejected configs stop startup before any module init hook runs.

The manifest's enabled value defaults to true; central configuration takes precedence. Disabled modules run no init, start, destroy, or cleanup work.

Dependencies​

Required dependencies must be registered and enabled. Optional dependencies are ignored when absent or disabled; when active, they still start before the dependent module.

export default defineModule({
	name: "quests",
	version: "1.0.0",
	dependencies: ["inventory"],
	optionalDependencies: ["analytics"],
	init: (context) => {
		if (context.isEnabled("analytics")) {
			// Enable the optional integration.
		}
	},
});

The graph is resolved once in deterministic name order. Missing required dependencies, disabled required dependencies, duplicate names, self-dependencies, duplicate dependency entries, and cycles are rejected. Versions are metadata in Phase 11; semantic-version constraints are intentionally not implemented.

Lifecycle and cleanup​

Startup follows:

Discover → Validate activation/config → Resolve dependencies → Init all → Start all

All dependency init hooks finish before a dependent initializes, and every active module finishes init before any module starts. Hooks may return void or Promise<void>.

Shutdown runs destroy and then owned Cleanup resources in reverse activation order. Startup failure performs the same rollback for modules whose initialization began. Cleanup is idempotent, and disabled modules allocate no cleanup owner visible to gameplay code.

The main runtime starts module lifecycle after the existing Service/Controller and Component kernels; on the server, PlayerLifecycle is also available before module initialization. It destroys modules before those lower-level systems.

Errors and performance​

Module failures are ModuleError or ModuleLifecycleError values with stable MODULE_* codes. Discovery failures continue to use DISCOVERY_FAILURE and include the manifest path.

  • Discovery and graph resolution happen only during startup.
  • Runtime lookups use maps; there is no polling or per-frame work.
  • Optional dependencies add no adapter or object when absent.
  • No Remote, Store, UI root, or Roblox Instance is created by the module system itself.
