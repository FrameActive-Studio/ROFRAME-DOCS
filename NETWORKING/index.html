Networking

Phase 4 provides strictly typed, server-authoritative communication over native Roblox RemoteEvent and RemoteFunction instances. TypeScript catches API mistakes during development; runtime Validators protect every client-to-server boundary.

Networking does not implement gameplay messages or persistence. Phase 5 Stores use one private named network built on this transport; application networks remain independent.

Define a network​

Keep definitions in a shared TypeScript module imported by both runtimes. Define each named network exactly once per runtime.

import { defineNetwork } from "@frameactive-studio/core";

export interface ClientToServerEvents {
	BuyItem: (itemId: string, amount: number) => void;
}

export interface ServerToClientEvents {
	ShowNotification: (message: string) => void;
}

export interface Requests {
	GetItemName: (itemId: string) => string;
}

export const gameNetwork = defineNetwork<
	ClientToServerEvents,
	ServerToClientEvents,
	Requests
>({ name: "Game" });

The same API is also available as RoFrame.defineNetwork(...).

Client-to-server events​

Every server handler requires a Validator. There is no unsafe handler overload.

import { validators } from "@frameactive-studio/core";
import { gameNetwork } from "shared/network";

const connection = gameNetwork.server.on("BuyItem", {
	validate: validators.tuple(
		validators.stringLength(1, 64),
		validators.integerRange(1, 100),
	),
	rateLimit: {
		calls: 5,
		perSeconds: 1,
	},
	permission: (player, itemId, amount) => {
		return canBuy(player, itemId, amount);
	},
	handler: (player, itemId, amount) => {
		// Perform authoritative server logic here.
	},
});

The client sends the matching event:

gameNetwork.client.fire("BuyItem", "sword", 1);

Unknown names, wrong argument counts, invalid values, denied permissions, and rate-limited calls never reach the handler.

Server-to-client events​

gameNetwork.server.fire(player, "ShowNotification", "Purchase complete");
gameNetwork.server.fireAll("ShowNotification", "Server restart soon");
const connection = gameNetwork.client.on("ShowNotification", (message) => {
	print(message);
});

Server-to-client payloads are statically typed. They do not require an untrusted-client Validator because the server is authoritative.

Requests and responses​

Requests use the network's single native RemoteFunction.

gameNetwork.server.handle("GetItemName", {
	validate: validators.tuple(validators.stringLength(1, 64)),
	rateLimit: { calls: 10, perSeconds: 1 },
	handler: async (_player, itemId) => {
		return await lookupItemName(itemId);
	},
});
const name = await gameNetwork.client.request("GetItemName", "sword");

Request handlers may return a value or a Promise. Failures are returned in an internal structured envelope and become a NetworkError on the client. Avoid long-running handlers because Roblox RemoteFunction calls yield the caller.

Validator API​

Built-in Validators:

  • validators.string
  • validators.number — finite numbers only
  • validators.boolean
  • validators.literal(value)
  • validators.numberRange(min, max)
  • validators.integerRange(min, max)
  • validators.stringLength(min, max) — UTF-8 length bound
  • validators.tuple(...) — exact argument count and types
  • validators.custom(predicate, issue)

Validators accept unknown and return a discriminated ValidationResult. A custom Validator should validate every relevant field, collection length, numeric range, and Instance constraint. If a Validator itself fails, the payload is rejected and logged.

Security pipeline​

Incoming client traffic follows this order:

Known name
→ Rate limit
→ Runtime validation
→ Permission hook
→ Handler

Types are never treated as security. Server handlers receive typed values only after validation succeeds. The rate limiter runs before validation so malformed spam is still bounded. Buckets are removed when a Player leaves.

The built-in limiter uses fixed windows. calls must be a positive integer and perSeconds must be positive.

Logging hooks​

Pass a logger when defining the network:

const network = defineNetwork<ClientEvents, ServerEvents, Requests>({
	name: "Game",
	logger: (entry) => {
		print(entry.level, entry.code, entry.name, entry.player?.Name);
	},
	onRateLimit: (context) => {
		print("Rate limited", context.player?.Name, context.name);
	},
});

Entries include the network, message name, direction, level, code, message, Player where applicable, and original cause where safe. Logger failures are isolated from dispatch. The default logger reports warnings and errors but does not log successful traffic, avoiding production overhead.

When Phase 12 DeveloperTools are enabled, the same rejected-message diagnostics are copied into a bounded development buffer. On-demand Network snapshots expose registrations, listener counts, directions, and rate-limit metadata, but never retain payloads or successful traffic. See DEVELOPER_TOOLS.md.

Cleanup​

on, handle, and client on return a cleanup-compatible connection:

this.cleanup.add(
	gameNetwork.server.on("BuyItem", {
		validate: validators.tuple(validators.string, validators.number),
		handler: () => {},
	}),
);

network.destroy() disconnects all listeners and clears rate-limit state. RoFrame.stop() first releases Stores and their private network, then destroys remaining registered networks before Components, Services, and Controllers shut down.

Remote layout and overhead​

Each network creates exactly two native Remote instances on the server:

ReplicatedStorage
└── RoFrameNetwork
    └── Game
        ├── Events    (RemoteEvent)
        └── Requests  (RemoteFunction)

The client uses WaitForChild with a bounded timeout; no polling is used. Events are multiplexed by a validated message name. Unknown names have no registered dispatch path and are rejected. Conflicting Instance classes or duplicate network definitions stop setup with a structured NetworkError.
