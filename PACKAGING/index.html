Packaging and releases

Package boundaries and status​

The runtime publishing target is GitHub Packages at https://npm.pkg.github.com, owned by FrameActive-Studio and linked to FrameActive-Studio/ROFRAME. Core and Cartoon UI are publish-enabled workspaces at 0.1.1 (private: false), but the workflow gate remains off until explicitly enabled. No package has been published by this migration. GitHub package visibility is initially private; it is separate from npm's package.json field named private.

The root and demo remain non-publishable. Camera and Animator remain non-publishable skeletons with disabled manifests (CameraModule / AnimatorModule); camera paths, timelines and adapters are not implemented. The current licensing metadata stays UNLICENSED, matching the repository's existing decision. No open-source license was added.

The explicit public exceptions are @frameactive-studio/cli and create-roframe, both configured with private: false and npmjs.org public access. Source remains in the private ROFRAME monorepo; runtime source and package access remain private. Neither public tool includes runtime packages. Registry account setup and first uploads are still pending.

Core provides the generic UI foundation. Its root exports do not load React; @frameactive-studio/core/ui contains client React APIs and UIController. The Cartoon UI root is client presentation; @frameactive-studio/cartoon-ui/module is its server-safe, inert manifest. Only explicit exports entries are public. Internal imports from another package's src/ or out/ are rejected by package validation. Camera is independent of Animator; future Animator adapters may orchestrate Camera. Neither package imports the other today.

Installation​

After the public tools' first release:

npm install -g @frameactive-studio/cli --@frameactive-studio:registry=https://registry.npmjs.org
npm create roframe@latest my-game

The scope override matters: npm registry routing is scoped, so the same @frameactive-studio scope cannot route CLI and Core to different registries by package name. Generated games pin the CLI's public tarball URL while retaining the private runtime scope mapping. create-roframe bundles its CLI dependency (and TypeScript) so it also installs under an existing GitHub scope mapping. See npm scope routing.

For this unpublished workspace repository:

rokit install
npm ci
npm run check

After publication, configure the consuming game's .npmrc with:

@frameactive-studio:registry=https://npm.pkg.github.com

Authenticate interactively with a GitHub personal access token (classic) that has read:packages and access to the package. Enter the token only in the npm login prompt; do not put it in source files or chat. Then install the packages:

npm login --scope=@frameactive-studio --auth-type=legacy --registry=https://npm.pkg.github.com
npm install @frameactive-studio/core
npm install @frameactive-studio/cartoon-ui @rbxts/react @rbxts/react-roblox

GitHub Packages requires authentication for npm package downloads, including public packages. In GitHub Actions, use the job's GITHUB_TOKEN when that repository has package access. Scope mapping affects every package in the organization scope, so public CLI installs need the override above; React and tooling continue to come from the normal npm registry. The monorepo itself installs its own libraries through workspace links without registry auth. See GitHub's npm registry guide.

Install Core explicitly in the consuming game. Optional modules use a peer rather than a bundled or nested Core dependency. Core's React peers are optional for server-only games; install them when using @frameactive-studio/core/ui.

import { RoFrame, Service, Controller, defineStore } from "@frameactive-studio/core";
// Client only:
import { UIController, Screen } from "@frameactive-studio/core/ui";
import { CartoonButton } from "@frameactive-studio/cartoon-ui";
// Server-safe manifest:
import CartoonUIModule from "@frameactive-studio/cartoon-ui/module";

roblox-ts 3 uses Node module resolution, so packages specify main (Luau), types (declarations), typesVersions for supported subpaths, and explicit exports. A consumer must include both scopes in its TypeScript configuration:

{
  "compilerOptions": {
    "typeRoots": ["node_modules/@rbxts", "node_modules/@frameactive-studio"],
    "types": ["types"]
  }
}

Map both scopes under the runtime's shared node_modules folder in Rojo:

{
  "rbxts_include": {
    "$path": "include",
    "node_modules": {
      "$className": "Folder",
      "@rbxts": { "$path": "node_modules/@rbxts" },
      "@rbxts-js": { "$path": "node_modules/@rbxts-js" },
      "@frameactive-studio": { "$path": "node_modules/@frameactive-studio" }
    }
  }
}

The demo's complete project lives in demo/default.project.json. The root project forwards there. Package project files map only generated out/; the TypeScript sources remain the source of truth. Client/server game output stays in StarterPlayerScripts/ServerScriptService, with shared code in ReplicatedStorage.

Building and validating​

The base TypeScript config holds shared compiler options. Package configs define source/output locations. Thin root tsconfig.<package>.json files let roblox-ts resolve npm's hoisted dependencies from the root; workspace build scripts select these explicitly. This avoids nested dependency symlinks and compiler patches. The demo production build has no aliases to library sources.

The packed consumer checks TypeScript and roblox-ts compilation, a Rojo place, exactly one Core package and runtime, and server code isolation. A second consumer installs and builds Core alone without React or optional modules. Tarballs go to ignored build/packages/; the place is build/PACKED_CONSUMER.rbxlx. Runtime archives allow only manifests, README/changelog/license files, source TypeScript and generated Luau/declarations. Cartoon UI also includes its source logo at src/assets/cartoon-ui-logo.png. CLI archives contain compiled Node JavaScript/declarations and documentation. The starter additionally bundles only CLI/TypeScript, materialized from public build artifacts because npm does not bundle hoisted workspace symlinks. Pack checks and offline installation tests verify both public executables without private runtime code or credentials. Node unit tests retain implementation-level imports and use a test-only barrel of actual pure Core implementations. Native adapters are validated by production compilation; Studio rendering, physics and multiplayer smoke tests remain manual.

Independent versions and Changesets​

Use Semantic Versioning: patch for fixes, minor for compatible features, major for breaking public API changes. Version only affected packages. The starter's exact bundled CLI dependency follows CLI version changes through Changesets. Peer dependency updates may require dependent version changes; Changesets computes them.

npm run changeset
npm run version:packages
npm run release:dry-run

The version script applies changesets, writes package changelogs and refreshes the root npm lockfile. Review all three together. Private libraries participate in versioning; the private demo is excluded. Private tags are disabled. For publish-enabled packages, registry-specific publishers upload only unpublished versions and create package-aware tags such as @frameactive-studio/core@0.1.1. The GitHub Packages migration changeset schedules a patch for Core and Cartoon UI; Core/Cartoon UI retain the merged 0.1.1 version; the separate registry-migration changeset schedules their next patch. Camera/Animator remain at 0.1.0.

CI and release workflow​

ci.yml runs for pull requests and main pushes with read-only repository access: clean install, dependency-tree validation, complete check, packed consumer, versioning dry run, documentation build and whitespace check. Pull requests receive no publishing credentials.

release.yml runs on main. The version job validates the same code and uses Changesets Action v1 with Changesets CLI v2 to create/update a Version Packages PR. The runtime publish job runs only when no pending changesets remain and repository variable ROFRAME_GITHUB_PACKAGES_PUBLISH_ENABLED equals true. It uses the github-packages environment, with contents: write for tags/releases and packages: write for registry uploads. The version job has no package-write permission.

The runtime publisher authenticates using NODE_AUTH_TOKEN: ${{ secrets.GITHUB_TOKEN }}. This job needs no npmjs.org account or OIDC permission. Runtime publishConfig.registry, scope mapping and the guarded release command all target https://npm.pkg.github.com. The guard also validates the exact repository, main ref, clean committed source, explicit gate, registry allowlist, licensing metadata and publish-enabled Core peers. Each publish command gets an explicit registry and scope override. Only a conclusive registry E404 permits an upload; authentication/network errors stop it.

Public npm tooling release​

The separate publish-npm job uses the npmjs environment and ROFRAME_NPM_TOOLS_PUBLISH_ENABLED=true. It can publish exactly @frameactive-studio/cli and create-roframe; runtime packages are excluded. npm run release:npm is guarded for Actions/main and uses that same allowlist. Both tools declare public npmjs.org access in publishConfig. Root/demo stay non-publishable, and repository visibility is unchanged.

For the first release, an npm account must control the frameactive-studio organization scope and the create-roframe name. Configure a granular publish token as the npmjs environment secret NPM_TOKEN, following npm's 2FA/token requirements. Never paste tokens into chat or commit them. Alternatively, once package settings exist, configure a trusted GitHub publisher for organization FrameActive-Studio, repository ROFRAME, workflow release.yml, environment npmjs, with direct publishing allowed. The workflow supplies id-token: write. See public package publishing and trusted publishers.

Provenance is explicitly disabled because the source repository remains private; npm documents that public provenance is unavailable for private source repositories. Independent versioning, archive checks, offline installs and publish-command tests run before the gated release. No account settings, secrets, repository visibility, release gates or actual uploads were changed by local preparation.

The first publish creates the GitHub package automatically and associates it with this repository via repository.url; it does not need a manual bootstrap publish on npmjs.org. Package visibility/access is managed through GitHub Packages settings and may inherit repository permissions. Organization package creation policy must permit the intended package visibility. See GitHub Actions package publishing.

Enabling the first GitHub Packages release​

  1. Commit/push the registry migration, including package scope changes, .npmrc, package metadata, lockfile and workflows. Scope and package names must be lowercase; our names start with @frameactive-studio/.
  2. Resolve the separate Actions PR policy described below. It controls the Changesets version PR; package-upload permission does not override it.
  3. Create/configure the github-packages GitHub environment and its main-branch restrictions or required reviewers as appropriate for this repository.
  4. Under Settings → Secrets and variables → Actions → Variables, add the repository variable ROFRAME_GITHUB_PACKAGES_PUBLISH_ENABLED with value true when publishing is intended. The older npmjs-oriented variable ROFRAME_NPM_PUBLISH_ENABLED is no longer used.
  5. Merge the migration to main. Changesets creates a Version Packages PR using the pending Core/Cartoon UI registry-migration patch changeset. Review versions, changelogs and the lockfile, then merge that PR. Its main push runs the publishing job and creates the first package versions on GitHub Packages.
  6. Verify the repository/organization Packages page and package access. Root/demo and Camera/Animator remain excluded. The first registry versions follow the reviewed version PR; the local Core/Cartoon UI versions are currently 0.1.1.

For later releases, add npm run changeset with the feature/fix, merge the feature PR, and then merge the generated version PR. npm run release is guarded for Actions and does not run locally. npm run release:dry-run updates only a temporary copy and does not upload packages. No GitHub settings, credentials, visibility or publishing variables are changed by the local migration.

Troubleshooting: Actions cannot create the version PR​

If Changesets reports GitHub Actions is not permitted to create or approve pull requests, check the repository's separate Actions policy. The release workflow already declares contents: write and pull-requests: write for its version job; those permissions alone do not enable the repository policy.

An authorized repository administrator can open ROFRAME Actions settings, go to Workflow permissions, enable Allow GitHub Actions to create and approve pull requests, and save. Keep the default workflow permissions on Read repository contents and packages permissions; the release job requests its additional permissions explicitly. This policy also permits approving PR reviews by appropriately authorized workflow tokens, so enabling it requires an intentional repository administration decision. The workflow does not approve or merge its version PR itself.

If organization policy prevents changing the setting, an organization owner must review the inherited policy under FrameActive-Studio Actions settings. The same Allow GitHub Actions to create and approve pull requests setting must be allowed there before the repository can enable it. Keep default token permissions restricted to read. After the organization permits it, enable the repository setting and rerun the failed Release jobs from its Actions page.

On 2026-10-16, the user approved enabling the ROFRAME repository setting, but GitHub rejected the update with HTTP 409 because the organization forbids it. The available CLI authentication cannot read/manage the organization policy (HTTP 403; organization administration permission is required). The repository reported can_approve_pull_request_reviews: false at that time. A later read during the GitHub Packages migration confirmed that it is now true, with default permissions still read. No organization policy was changed by this agent. The new publishing variable and github-packages environment have not yet been configured; no release rerun or package upload was started.

See GitHub's workflow permission documentation.

Migration compatibility​

Framework behavior and exported symbols were preserved. The former planned @roframe/* names are now @frameactive-studio/* so the package scope matches the GitHub organization; update game imports and registry/Rojo scope mappings. Consumer import paths and source locations changed intentionally: shared/core becomes @frameactive-studio/core, shared/ui becomes @frameactive-studio/core/ui, and modules/cartoon-ui becomes @frameactive-studio/cartoon-ui. UIController is exported by the Core UI entry. Existing root build/watch/serve/place commands remain available. Source-relative imports into the previous monolithic tree must migrate to package entries.
