Persistence

Phase 6 adds optional, server-only Store persistence. Production uses Roblox DataStoreService; development and tests can use the included in-memory adapter. Non-persistent Stores do not open a DataStore, start an autosave timer, or consume request budget.

Persistent Store definition​

The smallest configuration is persist: true:

import { defineStore } from "@frameactive-studio/core";

interface ProfileState {
	coins: number;
	level: number;
}

export const profileStore = defineStore({
	name: "Profiles",
	scope: "player",
	state: (): ProfileState => ({ coins: 0, level: 1 }),
	actions: {
		addCoins(amount: number) {
			this.coins += amount;
		},
	},
	persist: true,
	replicate: { coins: true, level: true },
});

Persistence is available for player, global, and custom scopes. The default DataStore name is RoFrame_<StoreName>; keys include the Store scope, for example player:12345.

Load, save, and release​

Persistent instances must be opened asynchronously. Calling create() on one is rejected to prevent defaults from overwriting saved data.

const profile = await profileStore.server.load(player);
profile.actions.addCoins(25);

await profileStore.server.save(player);    // Keep the session open
await profileStore.server.release(player); // Save, unlock, and destroy

server.destroy(...) also saves and releases a persistent instance. Both it and StoreDefinition.destroy() return Promises and should be awaited. Repeated concurrent load() calls for the same scope key share one load operation.

Phase 7 automatically loads persistent Player Stores before PlayerReady. Explicit server.load(...) remains available for global, custom, and advanced Player workflows; repeated loads for the same key share one operation.

Full configuration​

persist: {
	enabled: true,
	version: 3,
	dataStore: "PlayerProfiles",
	keyPrefix: "live:",
	autosave: { intervalSeconds: 60 },
	sessionLeaseSeconds: 180,
	retries: {
		maxAttempts: 3,
		baseDelaySeconds: 1,
	},
	migrations: {
		1: (oldState) => ({
			coins: oldState.coins as number,
			level: 1,
		}),
		2: (oldState) => ({
			coins: oldState.coins as number,
			level: oldState.level as number,
		}),
	},
}

Important bounds:

  • Versions are positive integers.
  • Autosave intervals are at least 30 seconds.
  • Session leases are at least 90 seconds and longer than the autosave interval.
  • Retry attempts are bounded to at most five.
  • Roblox DataStore names and generated keys are validated against their 50-character limit.

State is checked against the state factory's exact top-level shape and primitive/table categories. An optional Validator<TState> can perform deeper runtime validation. Unsupported values, cyclic tables, non-finite numbers, excessive depth, missing keys, and unexpected keys fail safely instead of replacing saved data.

Session safety​

Every load uses one atomic UpdateAsync operation to acquire a lease containing a unique server session ID and expiry time. Another server cannot load the same key while that lease is active. Autosave renews the lease; if another server takes over after expiry, the old server's next save fails with PERSISTENCE_SESSION_LOST instead of overwriting newer data.

autosave: false disables periodic state writes, but RoFrame still renews the existing lease at half its lifetime. Manual save, release, Player removal, and shutdown always capture current state.

Session safety reduces duplicate-session risk but cannot make Roblox DataStore globally transactional across multiple keys. Each Store scope key is independent.

Autosave, retries, and budget​

The persistence manager maintains one timer for the earliest active Store deadline—there is no Heartbeat loop and no timer per Player. Dirty Stores save only when due. Clean Stores renew their session record.

Native requests use UpdateAsync exclusively and wait for DataStoreService update budget for a bounded period. Transient adapter failures use bounded exponential backoff. Validation, migration, and session-conflict errors are not retried because retrying cannot repair them.

Persistence logs are opt-in:

RoFrame.configurePersistence({
	logger: (entry) => {
		print(entry.level, entry.operation, entry.storeName, entry.storeKey);
	},
});

Configure persistence before the first Store definition in that runtime.

Migrations​

Saved records carry an explicit schema version. Migrations run sequentially: migration 1 converts version 1 to 2, migration 2 converts 2 to 3, and so on. They execute inside the atomic load transformation and must be synchronous and deterministic.

Missing or failed migrations produce a structured PersistenceError. RoFrame leaves the old record intact and never silently falls back to default state. Data from a schema newer than the configured Store is also rejected.

Development mock​

Use the mock before defining Stores:

import { MockPersistenceAdapterFactory, RoFrame } from "@frameactive-studio/core";

const mock = new MockPersistenceAdapterFactory();
RoFrame.configurePersistence({
	adapterFactory: mock,
	sessionId: "studio-session",
});

The adapter provides seed(storeName, key, value), read(storeName, key), and reset(storeName?) for deterministic fixtures and local tools. Tests should use the mock and must never access production data.

The default backend is RobloxDataStoreAdapterFactory. In Studio, enable API Services only when intentionally testing the real DataStore backend; otherwise configure the mock.

Shutdown​

The central Player lifecycle emits PlayerRemoving, then saves and releases that Player's loaded Store sessions. A single BindToClose callback flushes all remaining sessions with bounded operations. RoFrame.stop() disconnects Player lifecycle listeners before awaiting the same idempotent Store shutdown path and destroying networking.

If the platform rejects every bounded save attempt, RoFrame reports the structured failure and lets the lease expire naturally rather than clearing or fabricating persisted data.

See PLAYER_LIFECYCLE.md for automatic Player Store loading, PlayerReady, and Character readiness ordering.
