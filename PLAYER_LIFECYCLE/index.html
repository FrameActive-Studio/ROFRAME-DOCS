Player and Character Lifecycle

Phase 7 provides one central, server-side lifecycle for Players, persistent profiles, and Characters. RoFrame starts it after all Services and Components have started, so systems can subscribe during onInit or onStart without wiring their own Players.PlayerAdded connection.

Signals​

import { PlayerLifecycle } from "@frameactive-studio/core";

PlayerLifecycle.onPlayerReady.connect((player) => {
	print(`${player.Name} has a loaded profile and may enter gameplay`);
});

PlayerLifecycle.onCharacterReady.connect((player, character) => {
	print(player.Name, character.GetFullName());
});

The complete order for a successful join is:

PlayerAdded
ProfileLoading
ProfileLoaded
PlayerReady
CharacterAdded
CharacterReady
CharacterRemoving
PlayerRemoving

CharacterAdded waits for PlayerReady. If a Character already exists while profile data is loading, it is retained and announced immediately after the Player becomes ready. CharacterReady fires once when the current Character contains both a Humanoid and a HumanoidRootPart. Child changes are observed with native events; no polling or Heartbeat loop is used.

Available signals are:

  • onPlayerAdded(player)
  • onProfileLoading(player)
  • onProfileLoaded(player)
  • onPlayerReady(player)
  • onCharacterAdded(player, character)
  • onCharacterReady(player, character)
  • onCharacterRemoving(player, character)
  • onPlayerRemoving(player)
  • onError(error)

The same singleton is available as RoFrame.playerLifecycle.

Automatic Store loading​

Every persistent Store with scope: "player" is automatically loaded between ProfileLoading and ProfileLoaded:

export const profiles = defineStore({
	name: "Profiles",
	scope: "player",
	state: () => ({ coins: 0 }),
	persist: true,
});

PlayerLifecycle.onPlayerReady.connect((player) => {
	const profile = profiles.server.get(player);
	if (profile === undefined) return;
	print(profile.state.coins);
});

Define persistent Player Stores during module discovery, before runtime startup. Non-persistent Player Stores remain explicit and are not created automatically. Global and custom persistent Stores also remain explicit because their keys are not tied to a Player join.

On PlayerRemoving, RoFrame emits the synchronous signal first, then saves and releases every loaded Player Store. RoFrame.stop() disconnects lifecycle listeners and awaits the same cleanup path before shutting down persistence and networking.

Failure behavior​

If any profile provider fails to load, ProfileLoaded, PlayerReady, and Character signals are not emitted. RoFrame reports a structured PlayerLifecycleError, releases any profile state that did open, and kicks the Player with a safe retry message. Persistence retries and session-lock behavior remain governed by the Phase 6 persistence configuration.

Lifecycle signal handler failures are isolated and reported through onError; they do not convert a successfully loaded profile into a profile-load failure. Keep handlers synchronous and move long-running work into explicitly managed tasks.

Cleanup and boundaries​

RoFrame owns one pair of native Player connections plus per-Player Character connections. Character readiness listeners disconnect once ready, on Character removal, on Player removal, and on runtime shutdown.

This phase does not add UI, gameplay events, spawn systems, or Phase 8 functionality.
