Stores

Phase 5 provides typed state, actions, cached getters, selector subscriptions, and server-authoritative replication. Phase 6 adds optional persistence without changing non-persistent Store behavior.

Define a Store​

Keep a definition in shared TypeScript and import it on both the server and client. Names are unique per runtime and may contain 1–64 valid UTF-8 characters.

import { defineStore } from "@frameactive-studio/core";

interface PlayerState {
	coins: number;
	level: number;
	internalFlags: string;
}

export const playerStore = defineStore({
	name: "PlayerProgress",
	scope: "player",
	state: (): PlayerState => ({
		coins: 0,
		level: 1,
		internalFlags: "",
	}),
	actions: {
		addCoins(amount: number) {
			this.coins += amount;
		},
	},
	getters: {
		isExperienced: (state) => state.level >= 10,
	},
	replicate: {
		coins: true,
		level: true,
		internalFlags: false,
	},
});

The same function is available as RoFrame.defineStore(...).

Scopes​

Each definition has one scope:

ScopeServer instance keyClient keyReplication audience
globalOne implicit global instanceImplicitEvery client
playerA PlayerImplicit Players.LocalPlayerOwning Player only
customA caller-provided stringSame stringExplicitly granted Players

Server creation is explicit:

const global = globalStore.server.create();
const progress = playerStore.server.create(player);
const party = partyStore.server.create("party-alpha");

Duplicate instances are rejected. Scope keys are isolated, so actions on one Player or custom key cannot mutate another instance.

Persistent Stores use the asynchronous server load() API instead of create(). See PERSISTENCE.md.

Clients load their authoritative initial snapshot before reading a Store:

const progress = await playerStore.client.load();
print(progress.state.coins);

const party = await partyStore.client.load("party-alpha");

Client views expose state, getters, and subscriptions only. They do not expose actions or patch, so authoritative mutation remains server-only.

Actions and patches​

Actions run with an isolated state context and preserve their declared argument and return types:

progress.actions.addCoins(25);
progress.patch({ level: 2 });

Synchronous and asynchronous actions are supported. On completion, only changed top-level keys are committed. Concurrent async actions do not overwrite unrelated keys with an old whole-state snapshot.

Change tracking is deliberately shallow for low overhead. Replace a nested table when it changes instead of mutating it in place:

this.settings = { ...this.settings, musicEnabled: false };

Store state keys are fixed by the state factory. Unknown keys and undefined values are rejected.

Getters and subscriptions​

Getters are computed once per Store version and cached until state changes:

if (progress.getters.isExperienced()) {
	print("Veteran player");
}

Subscriptions use selectors. A callback runs only when its selected value changes by strict equality, or by an optional equality function:

const connection = progress.subscribe(
	(state) => state.coins,
	(coins, previous) => {
		print(previous, "->", coins);
	},
);

connection.disconnect();

Connections are cleanup-compatible and become disconnected when their Store is destroyed. Subscriber callback failures are isolated and warned without interrupting other subscribers.

Replication and authority​

Only keys explicitly set to true in replicate cross the network. Initial loads send a versioned snapshot; later updates send only changed replicated keys. Stale or out-of-order patches are ignored on the client.

All Stores share one internal RoFrameStores network, backed by one native RemoteEvent and one native RemoteFunction. There is no polling. Snapshot requests have exact runtime string validation and a server-side rate limit. The server also checks scope authorization before returning data:

  • Global Stores are readable by all players.
  • Player Stores are readable only by their owning Player.
  • Custom Stores are readable only after an explicit grant.
partyStore.server.grant("party-alpha", player);
partyStore.server.revoke("party-alpha", player);

A grant immediately sends the current replicated snapshot. A revoke removes that client replica. Never place sensitive server data in replicate; TypeScript types are not a security layer.

State values sent through replication must be values Roblox Remotes can serialize. The Store layer does not encode unsupported Instances or cyclic tables.

Cleanup​

Destroy one instance through its scoped API, or destroy the complete definition:

await playerStore.server.destroy(player);
partyStore.client.destroy("party-alpha");
await playerStore.destroy();

Server destruction notifies the relevant replication audience. RoFrame.stop() destroys every Store, disconnects subscriptions, and releases the internal Store network before shutting down the remaining framework runtime.

When a Player leaves, their Player-scoped Store is destroyed automatically and their custom-scope grants are removed, preventing stale Player references.

Persistence remains opt-in. A Store without persist never opens a DataStore or consumes DataStore request budget.

Development inspection​

Phase 12 DeveloperTools can produce read-only Store definition and instance metadata on demand. State values are excluded unless snapshot({ includeStoreState: true }) is explicitly requested; that option can expose private player data and must remain local to controlled development sessions. See DEVELOPER_TOOLS.md.
